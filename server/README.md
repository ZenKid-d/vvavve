# vvavve BFF — прокси веб-версии

Без него браузерная версия не работает вовсе, и вот почему:

1. **CORS.** Ни один источник (`music.youtube.com`, `api-v2.soundcloud.com`,
   `api.music.yandex.net`, `api.vk.com`) не отдаёт `Access-Control-Allow-Origin`.
2. **Запрещённые заголовки.** Браузер не даёт JS выставлять `User-Agent`,
   `Referer`, `Origin` и `Cookie` — а InnerTube без них отвечает отказом.
3. **`<audio>` не умеет заголовки вообще.** Браузерный `just_audio` играет через
   этот тег, поэтому подписанные ссылки источников до него не доживают.

На Android ничего этого нет: приложение ходит к источникам напрямую, и прокси
ему не нужен.

## Endpoints

| Метод | Путь | Назначение |
|---|---|---|
| `GET/POST` | `/v1/api?u=<адрес>` | Прокси к API источников |
| `POST` | `/v1/sign` | Меняет ссылку потока на короткоживущую подписанную |
| `GET` | `/v1/stream?t=<пропуск>` | Аудио с поддержкой `Range` |
| `GET` | `/v1/healthz` | Проверка живости |

Клиент шлёт запрещённые браузеру заголовки с префиксом `X-Fwd-`; прокси снимает
префикс и ставит их наверх. Список того, что вообще разрешено восстанавливать,
закрытый — иначе клиент мог бы протолкнуть наверх что угодно.

## Почему подпись, а не обычная авторизация

Тег `<audio src>` не умеет слать заголовки, поэтому право на доступ к потоку
кладётся в сам адрес: HMAC-подпись плюс срок жизни 6 часов. Без этого
`/v1/stream?u=…` был бы открытым релеем на любой адрес в интернете.

Всё остальное защищено токеном Firebase, причём проверяется **подпись**, а не
только содержимое: полезная нагрузка JWT — обычный base64, и «проверка» полей
без подписи означала бы, что нужный токен выпишет себе кто угодно.

## Переменные окружения

| Переменная | Что это |
|---|---|
| `FIREBASE_PROJECT_ID` | Проект, чьи токены принимаем (`count0-8424b`) |
| `STREAM_SECRET` | Ключ подписи ссылок, минимум 32 символа. Утечёт — ссылки сможет выписывать кто угодно |
| `ALLOWED_ORIGIN` | Адрес веб-версии, например `https://zenkid-d.github.io` |
| `PORT` | По умолчанию 8080 |

Сервис падает на старте, если что-то из первых трёх не задано: отдавать 500 на
каждый запрос хуже, чем не подняться.

## Развёртывание

```bash
docker build -t vvavve-bff server/
```

```bash
docker run -d --restart=always -p 8080:8080 \
  -e FIREBASE_PROJECT_ID=count0-8424b \
  -e STREAM_SECRET="$(openssl rand -hex 32)" \
  -e ALLOWED_ORIGIN=https://zenkid-d.github.io \
  --name vvavve-bff vvavve-bff
```

Спереди — Caddy, он сам получит сертификат:

```
bff.example.org {
  reverse_proxy localhost:8080
}
```

### Требования к машине

Сервис перекладывает байты, а не считает: упор в трафик и в IP, не в процессор.
2 vCPU / 2 ГБ / 20 ГБ диска, порт 100 Мбит, безлимитный трафик (час
прослушивания ≈ 70 МБ).

**Выделенный статический IPv4 обязателен.** Ссылки googlevideo привязаны к
адресу, с которого шёл резолв: если резолв и поток уйдут с разных адресов,
каждый ютуб-трек отдаст 403. По той же причине не годятся Cloudflare Workers и
Cloud Run без Cloud NAT.

**Адрес в РФ** нужен Яндекс.Музыке — она блокирует запросы извне. Если Google
начнёт хуже относиться к российским диапазонам, список хостов позволяет
расщепить выход: Яндекс с российского адреса, `youtubei` и `googlevideo` —
через зарубежный. Расщеплять надо по хосту целиком, иначе снова разъедутся
резолв и поток.

## Сборка веб-клиента

```bash
flutter build web --release -t lib/main_web.dart --dart-define=BFF_URL=https://bff.example.org --dart-define=APP_VERSION=3.2.2
```

Без `BFF_URL` веб-сборка соберётся, но поиск и звук работать не будут.
